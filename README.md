## How updates work

Two GitHub Actions workflows run automatically on every push to `main`. Which one fires depends on what files changed.

### Changing lab content → `docs/`

Edit any file inside `docs/` and push to `main`.

```bash
git add docs/
git commit -m "update lab content"
git push origin main
```

**What happens:** `deploy-pages.yml` detects the change, builds the MkDocs site, and deploys it to GitHub Pages. The live site updates in ~1 minute. No new release is created.

---

### Changing an app → `src/`

Edit files inside `src/ticket-app-django/` or `src/ticket-api/` and push to `main`.

```bash
git add src/
git commit -m "update app"
git push origin main
```

**What happens:** `release-apps.yml` detects the change, auto-increments the version tag (e.g. `v0.1` → `v0.2`), builds fresh ZIPs of both apps, and publishes them as a new GitHub Release. The download links in the docs (`/releases/latest/download/...`) automatically point to the new ZIPs — no manual steps needed.

---

### Changing both docs and an app

Just push everything together.

```bash
git add .
git commit -m "update docs and app"
git push origin main
```

**What happens:** Both workflows fire in parallel — the site redeploys and a new release with updated ZIPs is published simultaneously.

---

### What never needs manual work

- **Version tags** — auto-generated by the release workflow
- **Download links** — always point to `/releases/latest/`, so they never need updating
- **Site deployment** — triggered automatically on every push to `main`
